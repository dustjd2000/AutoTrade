# AI 매도 판단 검증 + 매도 프롬프트 자동 수정 — 설계

- 날짜: 2026-09-22
- 상태: 설계 승인됨 (구현 전)
- 관련: PRD 5.5-B "AI 매도 판단", 5.12 "추천 검증", 5.13 "프롬프트 자동 수정", 10절 "AI 매도 판단 기준을 순수익으로 바꾼다"

## 1. 배경과 목적

2026-09-22에 삼성생명이 아침 전망의 하방선(293,500원)을 10:20에 깬 뒤에도 AI가 "손실은 손절선이
관리한다"로 15:15까지 보유해 약 -17,300원(순)으로 끝났다. 같은 날 exit 프롬프트를 v2로 고쳤지만,
고친 것이 실제로 순수익을 늘리는지 확인할 수단이 없다.

- AI 매도 판단은 **메모리와 로그 텍스트에만** 남는다 (`TradingEngine.note_ai_exit_result`는 마지막
  한 건만 UI용으로 든다). 엔진 재시작으로 사라진다.
- 종목별 당일 순손익 고점(`DrawdownTracker`)도 메모리라 재시작하면 초기화된다. 2026-09-22 11:00
  판단은 실제 고점 -0.73% 대신 -2.91%를 봤고, 09:05~09:17 구간 고점은 기록 자체가 없다.

목적: **매일 AI 매도 판단을 순수익 잣대로 검증해 남기고, 표본이 쌓이면 매도 프롬프트를 자동으로
고친다.** 추천 쪽의 15:35 검증(5.12) → 자동 수정(5.13) 구조를 매도 쪽에 그대로 옮긴다.

### 평가 잣대 (이 설계 전체에 적용)

**순손익(수수료·세금 차감)이 플러스로 확정됐는가.** 종가보다 나은 값에 팔았는지, 다른 시점보다
덜 잃었는지는 성공 기준이 아니다. 판단은 두 질문으로 본다.

1. 보유 중 순이익 기회가 있었나 (순손익 고점 > 0) — 있었다면 확정했나 (최종 순손익 > 0)
2. 기회가 없었다면, 시나리오가 깨진 뒤 손실을 얼마나 일찍 끊었나

## 2. 기록 — 재시작에도 남게

### 2.1 `ai_exit_decisions` 테이블

판단 한 건(종목 하나)마다 한 줄.

| 컬럼 | 타입 | 내용 |
|---|---|---|
| id | INTEGER PK | |
| day | TEXT | 거래일 (ISO date) |
| at | TEXT | 판단 시각 (ISO datetime) |
| ticker / name | TEXT | |
| sell | INTEGER | 1=매도 판정, 0=보유 |
| ok | INTEGER | 1=정상 응답, 0=LLM 실패·타임아웃·형식 오류 (이때 sell=0) |
| reason | TEXT | 그 종목의 판정 사유 (실패면 실패 문구) |
| net_return | REAL | 판단 시점 순손익률 (비율) |
| peak_return | REAL | 판단 시점 당일 고점 순손익률 (없으면 NULL) |
| current_price | REAL | |
| exit_prompt_version | TEXT | 그 판단에 쓰인 매도 프롬프트 버전 |

- 쓰는 곳: `runtime.run_ai_exit_cycle`. 판정을 받은 직후(매도 실행 전)에 보유 종목 전부를 쓴다.
  응답에서 빠진 종목은 sell=0, reason="(응답 없음 — 보유로 처리)".
- 쓰기 실패는 로그만 남기고 삼킨다 — 기록 실패가 매도를 막으면 안 된다.

### 2.2 `position_peaks` 테이블

| 컬럼 | 타입 | 내용 |
|---|---|---|
| day | TEXT | |
| ticker | TEXT | |
| peak_return | REAL | 당일 순손익 고점 (비율) |
| peak_at | TEXT | 그 고점 시각 |
| peak_price | REAL | 그 고점의 현재가 |
| | | UNIQUE (day, ticker) — upsert |

- `DrawdownTracker`가 새 고점을 찍을 때 영속화한다. 틱마다 쓰지 않게 **종목당 5초에 한 번**으로
  묶고(그 사이 더 높은 고점은 다음 쓰기에 실린다), 마지막 미기록 고점은 AI 판단 사이클 시작과
  15:15 강제청산 직전에 한 번 더 비운다(flush).
- 엔진 시작(`TradingEngine.start`) 때 오늘 날짜의 값을 읽어 트래커를 **복원**한다(`seed`). 복원된
  고점은 "이미 발동 여부를 모르는" 상태라 무장(armed)한 채로 둔다 — 복원 직후 현재값이 고점보다
  임계값 이상 낮으면 한 번 앞당겨질 수 있고, 그것은 의도된 동작이다(재시작 전에 발동했어야 할
  반납이다).
- 08:40 일일 초기화는 메모리만 비운다 — 테이블은 날짜 키라 어제 값이 오늘에 섞이지 않는다.
- **고점 추적은 AI 매도 판단이 꺼져 있어도 돈다.** 지금은 `_track_exit_drawdown`이
  `ai_exit_enabled`가 꺼져 있으면 바로 돌아가는데, 검증의 "순이익 기회"는 AI를 끈 날에도 의미가
  있다. 조기 호출 트리거는 `ai_exit_due`가 이미 `ai_exit_enabled`를 먼저 보므로 영향이 없다.
- **동작 변화**: 재시작 후 AI 프롬프트의 "되돌림" 줄이 복원된 고점을 쓴다. 엔진이 꺼져 있던
  구간의 고점은 여전히 잡히지 않는다 (분봉 TR ka10080은 미구현 — 범위 밖).

## 3. 15:35 매도 판단 검증 (`DailyWorkflow.review_exits`)

### 3.1 순서

15:35 스케줄 등록 순서(= 큐 순서):
리포트 → 추천 검증 → 추천 프롬프트 수정 → **매도 판단 검증** → **매도 프롬프트 수정**.
둘 다 `touches_orders=False`(별도 스레드) — LLM 호출이 있다.

### 3.2 대상과 수치

대상은 **그날 매도 체결이 있는 종목**(trades의 sell·filled 행). 전일 이월분도 자연히 포함된다.
종목마다 계산한다.

- 최종 순손익 = 당일 그 종목 매도의 `realized_pnl` 합 − 당일 그 종목 매수·매도의 수수료·세금 합.
  realized_pnl을 모르는 행(평단 불명)이 있으면 그 종목은 "순손익 모름"으로 표시하고 평가에서 뺀다.
- 최종 순손익률 = 최종 순손익 / (평단 × 매도 수량)
- 보유 중 고점 = `position_peaks` (없으면 "고점 모름")
- 판정 분류 (코드가 정한다, LLM이 아니다):
  - `captured` — 최종 순손익 > 0
  - `missed` — 고점 > 0 이었는데 최종 ≤ 0 (순이익 기회를 놓침)
  - `no_chance` — 고점 ≤ 0, 최종 ≤ 0
  - `unknown` — 고점 또는 순손익을 모름
- 놓친 폭 = 고점 − 최종 순손익률 (고점을 알 때만)
- 청산 사유 = 마지막 매도 행의 `exit_reason`
- 그날의 판단 이력 = `ai_exit_decisions`에서 그 종목 행 전부

### 3.3 LLM 평가문 (`src/llm/exit_reviewer.py`, 새 모듈)

`reviewer.py`와 같은 꼴(스키마 강제, 실패 시 None, 별도 버전 상수 `EXIT_REVIEW_PROMPT_TEMPLATE_VERSION`).

- 입력: 종목마다 3.2의 수치 + 판단 이력(시각·순손익률·고점·판정·사유) + 아침 전망/목표 매도가.
- 시스템 프롬프트가 못 박는 것:
  - 잣대는 1절의 평가 잣대 그대로. "덜 잃었다", "종가보다 높게 팔았다"는 잘한 점이 아니다.
  - 판단마다 "그 시점에 알 수 있던 정보로" 평가한다 — 사후 가격을 근거로 그 시점 판단을 탓하지
    않는다. 다만 "그 시점 데이터가 이미 매도 근거를 보여줬는데 보유했다"는 지적한다.
  - 수치를 인용한다. 다음 프롬프트 수정 제안은 하지 않는다 (그건 튜너의 일).
- 출력: `{"reviews": [{ticker, review}]}` — 종목당 두세 문장.

### 3.4 저장과 메일

`exit_reviews` 테이블 — 종목당 한 줄, UNIQUE (day, ticker):
day, ticker, name, exit_prompt_version(그날 마지막 판단의 버전, 판단이 없으면 NULL), net_pnl,
net_return, peak_return, outcome(`captured`/`missed`/`no_chance`/`unknown`), exit_reason,
decision_count, review.

메일: 매도가 있던 날만 한 통(`templates.exit_review_email`). 맨 위에 당일 합계(순손익, 분류별 건수),
그 아래 종목마다 수치·판단 이력·평가문. 평가문이 없으면 수치만으로 보낸다.

## 4. 매도 프롬프트 자동 수정 (`DailyWorkflow.tune_exit_prompt`)

### 4.1 프롬프트를 절 파일로 뺀다

`build_exit_system_prompt`의 본문을 절로 나눈다.

| 키 | 절 | 편집 |
|---|---|---|
| `role` | 역할 (순수익 목적) | 잠금 — 사용자가 정한 목적 |
| `default_hold` | 기본은 보유입니다 | 잠금 — 안전장치 |
| `loss_positions` | 손실 중인 종목 | **편집 가능** |
| `time` | 시간 | **편집 가능** |
| `criteria` | 판단 기준 (되돌림·아침 전망·장중 공시) | **편집 가능** |
| `reason_format` | reason 작성 지침 | 잠금 — 출력 형식 계약 |

- 편집 가능한 세 절만 `data/exit_prompt/<key>.md`로 둔다. 파일이 없거나 깨졌으면 코드의
  `DEFAULT_EXIT_PROMPT_SECTIONS`로 폴백. 잠긴 절은 코드 상수 그대로.
- `build_exit_system_prompt`가 매 호출마다 파일을 읽는다 — 엔진 재시작 없이 다음 판단에 반영.
- `PromptStore`를 일반화한다: 생성자가 `section_order`, `defaults`, `default_version`을 받는다
  (기본값은 지금의 추천 값 그대로라 기존 호출부는 바뀌지 않는다). 매도용은
  `PromptStore(Path("data")/"exit_prompt", EXIT_PROMPT_SECTION_ORDER, DEFAULT_EXIT_PROMPT_SECTIONS,
  EXIT_PROMPT_TEMPLATE_VERSION)`.
- 버전: 파일이 없으면 `EXIT_PROMPT_TEMPLATE_VERSION`("v2"), 고치면 날짜 표기(`20260929`,
  같은 날 두 번째부터 `-2`) — `next_version` 재사용. 판단 기록(2.1)에 이 버전이 남는다.

### 4.2 튜너 (`src/llm/exit_tuner.py`, 새 모듈)

`tuner.py`와 같은 꼴. 입력:
- 버전별 성과: 건수, `captured`/`missed`/`no_chance` 건수, 순손익 합계·평균, 평균 놓친 폭
- 최근 10거래일 `exit_reviews` 개별 결과(수치·평가문) + 그 종목들의 판단 이력 요약
- 현재 편집 가능한 세 절 전문 + 잠긴 절(참고용)
- 직전 변경 이유 이력(최근 5개) — 되돌림 왕복 방지

출력: `{change, reason, sections}`.

### 4.3 안전장치 (코드가 강제)

- **표본 게이트**: 현재 버전으로 검증된 종목(`exit_reviews`에서 `outcome != unknown`)이
  **10건 미만이면 튜너를 부르지 않는다.** LLM 판단 이전에 코드가 막는다.
- **한 번에 1절만.** 원본 개수부터 센다 — 2절 이상이 오면 전체를 버린다 (추천 튜너의 규약).
- 편집 가능한 세 키 외의 키는 버린다. 본문 50자 미만은 버린다.
- 튜너 시스템 프롬프트: 잣대는 순수익, 표본 부족하면 고치지 말 것, 직전 변경을 되돌리지 말 것,
  잠긴 절과 모순되지 않을 것, 데이터가 말하지 않는 것을 지어내지 말 것.
- 고친 날만 메일(`templates.exit_prompt_tuning_email` — 추천용 `prompt_tuning_email`을 재사용할
  수 있으면 재사용). 고치지 않는 날이 정상이다.

## 4-A. 월 순수익 게이트 — 잘 되고 있으면 두 프롬프트 모두 고치지 않는다

**이번 달 순수익률이 설정값 이상이면 추천 프롬프트 수정(`tune_prompt`, 기존)과 매도 프롬프트
수정(`tune_exit_prompt`, 신규)을 둘 다 건너뛴다.** 월 순수익은 추천과 매도가 함께 만든 결과라,
잘 되고 있을 때는 어느 쪽도 건드리지 않는다.

- **설정**: `.env`의 `TUNE_SKIP_MONTHLY_RETURN_PERCENT` (기본 5). 퍼센트 설정 패턴 그대로
  `tune_skip_monthly_return_percent` 필드 + `tune_skip_monthly_return_ratio` 프로퍼티.
  UI에서 **1~10%, 0.5 단위**로 고른다. `_save_settings` 경로라 바꾸면 엔진이 재시작된다(다른 설정과
  같다). `Settings.validate()`가 범위(1~10)를 강제한다.
- **계산**: 일일 리포트와 같은 식 — 이번 달 1일~오늘 순손익(`monthly_summary(...).net_pnl`) ÷
  (현재 총자산 − 그 순손익). 총자산은 `account.get_balance_snapshot()`. 계산은 `DailyWorkflow`의
  헬퍼 하나(`_monthly_net_return()`)로 두고 리포트와 게이트가 함께 쓴다.
- **판정 순서**: 각 튜너 단계의 맨 앞, LLM 호출 전에 코드가 본다. 매도 튜너에서는 표본 게이트(4.3)보다
  먼저 본다. 건너뛰면 로그에 "이번 달 순수익 +x.xx% ≥ 기준 y.y% — 프롬프트를 고치지 않습니다"를 남긴다.
  메일은 보내지 않는다(고치지 않는 날이 정상).
- **조회 실패**: 잔고 조회가 실패하거나 분모가 0 이하면 **고치지 않는다**. 아무것도 바꾸지 않는 것이
  기본 상태다.
- 검증(추천 검증·매도 판단 검증)과 그 메일은 게이트와 무관하게 매일 돈다 — 고치지 않을 뿐, 기록은
  계속 쌓인다.

## 5. 실패 처리

어떤 실패도 매매를 막지 않는다.

- 판단·고점 기록 실패 → 로그만, 매도·손절은 그대로
- 검증 LLM 실패 → 수치만으로 메일
- 튜너 실패·안전장치 전부 걸림 → 고치지 않음
- 프롬프트 파일 손상 → 코드 기본값 폴백 (`PromptStore._read`가 이미 처리)

## 6. 테스트

- `position_peaks`: 새 고점 upsert, 5초 묶음, flush, 재시작 후 seed 복원, 날짜가 다르면 복원 안 됨
- 고점 추적이 AI 매도 판단 OFF에서도 돈다
- `ai_exit_decisions`: 판정/실패/응답 누락 종목 기록, 기록 실패가 매도를 막지 않음
- 검증 분류: captured / missed / no_chance / unknown 경계, 순손익 계산(수수료 포함), 이월분
- 검증 메일: 매도 없는 날 미발송, 평가문 없을 때 수치만
- 매도 프롬프트 파일화: 파일 없음 → 기본값과 지금의 v2 본문이 같다, 파일 반영이 재시작 없이 됨
- 튜너 안전장치: 표본 게이트(9건 → 호출 안 함, 10건 → 호출), 2절 → 전체 폐기, 잠긴 절 키 무시,
  짧은 본문 무시
