# AI 매도 판단을 종목별로 — 설계

작성 2026-09-19. 관련: PRD 5.5-B "AI 매도 판단", `docs/superpowers/specs/2026-09-18-position-level-stop-loss-design.md`.

## 배경

2026-09-18에 손절을 종목별로 되돌리면서, 청산 경로에서 **AI 매도 판단만 전량으로 남았다.**

| | 판정 단위 |
|---|---|
| 손절 | 종목별 (2026-09-18) |
| 이익 반납 감시 트리거 | 종목별 |
| 장중 공시 트리거 | 종목별 |
| **AI 매도 판단** | **보유 목록 전량** |

트리거는 종목별인데 판단은 전량이라, 한 종목의 신호가 보유 전체의 운명을 정한다.

**그리고 AI가 지금 하는 일이 의도와 반대다.** 손절선이 -5%인데 AI가 판 6번의 시점 합산 손익은
-2.45% / -1.85% / -0.46% / -0.26% / -0.19% / +0.27%다. 즉 **손실 종목을 손절선 한참 전에 파는
장치로 동작하고 있고**, 그래서 이익이 자랄 시간이 없었다. 관측된 종목별 당일 최대 이익이
+2.17%에 그친 것도 이 때문이다.

합산이 개별을 가린 사례:

| 날짜 | 상황 | 전량 판정의 결과 |
|---|---|---|
| 09-18 | NC +0.97% / NH투자증권 -1.19% | 합산 -0.19% → 둘 다 정리 |
| 09-15 | 현대차 +0.18% / 삼양식품 -2.29% | 합산 -1.85% → 둘 다 정리 |
| 09-16 | 산일전기 고점 +2.17% / HD건설기계 -0.75% | 보유로 넘겼다가 -0.12%에 둘 다 정리 |

## 결정된 것과 그 이유

**A. AI 매도 판단을 종목별로 바꾼다.** 트리거 단위와 판단 단위를 일치시킨다.

**B. AI의 주 목적을 "오른 종목의 이익을 제때 확정하는 것"으로 둔다.** 익절 자동 청산을
2026-09-09에 걷어낸 뒤 AI가 유일한 이익 실현 수단인데, 실제로는 손실 구간 매도에 쓰이고 있다.
무게중심을 옮긴다.

**C. 손실 중인 종목도 AI가 판단하되 문턱을 높인다.** "아침 시나리오가 무너졌다"는 구체적 근거가
있을 때만 팔고, 단순히 마이너스라는 이유로는 팔지 않는다. 하방은 손절선이 맡고 있다.

> 설계 검토에서 "AI는 이익 구간 종목만 보게 닫자"는 대안이 함께 논의됐다. 조급한 매도가 구조적으로
> 불가능해지는 대신 시나리오가 깨진 종목을 -5%까지 들고 가야 한다. **사용자가 열어두는 쪽을 택했다.**

**D. 프롬프트에서 합산 정보를 뺀다.** 2026-09-18에 손절선을 뺀 것과 같은 논리다 — 판단이 종목별인데
합산 숫자를 주면 AI가 그것으로 판단한다. **지시보다 데이터가 세다**는 것이 그때 확인됐다(시스템
프롬프트가 "손절선은 신경 쓰지 말라"고 못박았는데도 AI가 주된 근거로 썼다).

## 범위 밖

- **15:15 강제청산은 전량 그대로.**
- **`_execute_portfolio_exit` 경로를 새로 만들지 않는다** — 종목별 손절이 이미 쓰는 경로에 대상
  목록을 좁혀 넘긴다.
- **호출 주기(30분)·호출 창(매수 +15분 ~ 15:00)·하루 상한·실패 시 "팔지 않음"은 그대로.**
- **이익 반납 감시와 공시 트리거의 동작은 그대로.** 판단 단위가 맞춰질 뿐이다.
- **`exit_advisor`의 비스트리밍 120초 타임아웃은 이번에 고치지 않는다.** 2026-09-16에 추천 경로에서
  고친 것과 같은 문제가 남아 있고(응답이 길어지면 조용히 실패 → "팔지 않음"), 종목별로 바뀌면 응답이
  길어져 위험이 커진다. 성격이 다른 수정이라 섞지 않는다 — 이 작업 다음에 이어서 한다.

## 1. 응답 형태

`EXIT_SCHEMA`를 종목별 배열로 바꾼다.

```json
{"decisions": [{"ticker": "005930", "sell": true, "reason": "..."}]}
```

- `ExitDecision(sell, reason)` → 종목별 판정을 담는 구조로 바꾼다. 팔 종목코드 목록과 종목별 사유를
  꺼낼 수 있어야 한다.
- **응답에서 빠진 종목은 보유**로 떨어진다. `sell`이 불리언 `true`가 아니면 보유인 기존 원칙 그대로다.
- **응답에 없는 티커(환각)는 버린다.** 보유하지 않은 종목을 팔라고 해도 무시한다.
- 파싱 실패·형식 오류는 그 주기 전체를 "팔지 않음"으로 떨어뜨린다 (기존과 동일).

## 2. 시스템 프롬프트

**`## 역할`을 다시 쓴다.** 지금은 "종목별로 골라 파는 매도는 없습니다 — 판단은 항상 보유 목록 전체에
대해 한 번입니다"로, 정확히 반대를 말하고 있다. 새 역할은 **"보유 종목을 하나씩 보고, 지금 이익을
확정할 때인지 판단한다"** 이다.

**`## 기본은 보유`를 종목별로 다시 쓴다.** 판단 대상이 N배가 되면 매도 기회도 N배다. 여기에 **손실
구간 종목의 문턱**을 새로 단다 — 손실 중인 종목은 아침 시나리오가 무너졌다는 구체적 근거가 있을
때만 팔고, 마이너스라는 사실 자체는 근거가 아니다. 하방은 손절선이 맡는다.

**판단 기준 1(되돌림)·2(아침 전망의 유효성)·3(장중 공시)은 그대로 둔다.** 이미 종목 단위로 서술돼
있고, 되돌림과 "아침 목표 매도가를 이미 넘어섰다면 달성된 시나리오"가 곧 이익 확정 장치다. 적용
단위가 종목별임만 명시한다.

## 3. user prompt에서 합산을 뺀다

빼는 것: 합산 순손익률(`## 현재`), 합산 당일 고점, 궤적의 합산 열.

남기는 것: 종목별 순손익률, 종목별 되돌림(고점 → 현재, 반납폭), 종목별 궤적, 아침 목표 매도가·근거·
전망, 당일 공시, 15:15까지 남은 시간.

`build_exit_user_prompt`에서 `portfolio_return`·`portfolio_peak` 인자가 빠진다. `TracePoint`는
`per_ticker`만 렌더한다(자료구조 자체는 그대로 둔다 — UI와 로그가 쓴다).

**UI 표시와 로그의 합산 값(`portfolio_return`, `portfolio_net_pnl`)은 그대로 유지한다** — 사람이 보는
용도다.

## 4. 실행

`run_ai_exit_cycle`에서:

1. 판정을 받는다. 팔 종목이 없으면 기존처럼 "보유 유지"로 로그·UI 기록만 남기고 끝낸다.
2. `engine.exit_candidates(force=True)`로 보유를 다시 읽는다 (LLM 응답 대기 중 손절이 먼저 정리했을
   수 있다 — 기존 장치 그대로).
3. 그중 **팔기로 한 종목만** 골라 `_execute_portfolio_exit(targets, ExitReason.AI_JUDGMENT, note=...)`에
   넘긴다.
4. 판정 대상이 이미 전부 정리됐으면 그 사실을 로그로 남기고 끝낸다.

`note`에는 종목별 사유를 묶어 넣는다 — 청산 로그와 알림 메일이 "왜 팔았는지"를 종목마다 담아야 한다.

`engine.note_ai_exit_result(...)`는 UI 보유 종목 표가 읽는 마지막 판단 기록이다. 종목별 판정을 담도록
맞춘다.

## 받아들인 위험

- **이익 확정이 실제로 늘어날지는 돌려봐야 안다.** 프롬프트 판단이라 보장할 수 없다.
- **매도가 잦아질 수 있다.** 판단 대상이 N배가 되어 문턱이 구조적으로 낮아진다. "기본은 보유"와
  손실 구간 문턱을 프롬프트로 지켜야 하는데, 손절선 사례에서 보듯 프롬프트만으로는 약할 수 있다.
  며칠 돌려 보고 되돌릴 수 있게 커밋을 항목 단위로 나눈다.
- **응답이 길어져 타임아웃 위험이 커진다.** 종목마다 사유를 쓰므로 출력이 늘어난다. 비스트리밍
  120초가 그대로라 조용히 실패할 수 있고, 그때는 "팔지 않음"으로 떨어진다 — 이익 확정이 목적인데
  실패가 보유로 떨어지는 구조는 그대로다. 다음 작업에서 스트리밍으로 고친다.
- **한 종목이 팔린 뒤 남은 종목의 판단은 다음 주기(최대 30분 뒤)다.** 즉시 재판단하지 않는다.
