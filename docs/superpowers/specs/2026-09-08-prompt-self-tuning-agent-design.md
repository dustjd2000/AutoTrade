# 추천 프롬프트 자동 수정 에이전트 — 설계

작성 2026-09-08

## 배경

2026-09-03에 추천 검증 기능을 붙여, 매일 15:35에 그날 추천한 종목의 실제 움직임과 목표가
도달 여부가 `recommendations` 테이블에 쌓이기 시작했다. 지금은 그 데이터를 사람이 열어 봐야만
쓸모가 생긴다.

이 설계는 그 데이터를 매일 읽고 **추천 프롬프트를 스스로 고치는 에이전트**를 붙인다.
사람 승인 없이 자동으로 반영된다.

## 결정된 것과 그 이유

| 항목 | 결정 | 이유 |
|---|---|---|
| 수정 범위 | 판단·서술 지침 다섯 절만 | 나머지 절은 코드와 계약 관계라, 고치면 프롬프트와 코드가 소리 없이 어긋난다 (아래 "잠그는 이유") |
| 판단 근거 | 최근 10거래일을 `prompt_version`별로 묶어서 | 매일 고치면 버전마다 하루치 표본뿐이라, 버전별로 나눠야 자기 수정의 효과를 볼 수 있다 |
| 사람 개입 | 고친 날만 메일 + 파일 이력 | 완전 자동이라 개입 지점이 없다. 바뀐 걸 알아야 되돌릴 수 있다 |
| 승인 절차 | 없음 (완전 자동) | 사용자 결정 (2026-09-08). 아래 "받아들인 위험" 참고 |

## 잠그는 이유 — 프롬프트와 코드의 계약

시스템 프롬프트의 일부는 코드가 강제하는 규칙을 문장으로 적어 둔 것이다. 문장만 바뀌면
LLM은 새 지시를 따르는데 코드가 그 결과를 잘라내, **조용히 추천이 0종목이 되는** 식으로
나타난다.

| 프롬프트 | 강제하는 코드 |
|---|---|
| 절대 규칙 1 (후보 목록 내에서만) | `drop_unknown_tickers` |
| 절대 규칙 4 + 추천 유형 (`rebound`만) | `drop_other_setups` |
| 절대 규칙 6 (현재가 ±5%) | `normalize_target_price` |
| 절대 규칙 7 (매도가 > 매수가) | `warn_invalid_sell_targets` |

또한 `역할`과 `절대 규칙`만 `target_count`를 f-string으로 보간한다. 열어 줄 다섯 절은
순수 텍스트라 파일로 빼도 보간 로직이 필요 없다.

## 범위 밖

- 매수·청산 로직은 건드리지 않는다. 이 에이전트는 프롬프트 텍스트만 바꾼다.
- 기존 메일 네 종류(추천 / 매수 결과 / 일일 리포트 / 추천 검증)는 그대로 둔다.
- 사용자 프롬프트(`build_user_prompt`)는 대상이 아니다 — 데이터를 나열하는 자리라 판단이 없다.
- 검증 평가 프롬프트(`src/llm/reviewer.py`)도 대상이 아니다.
- 나쁜 수정을 자동으로 되돌리는 기능은 만들지 않는다. 되돌리기는 사람이 이력 파일로 한다.
- AI 매도 판단(30분 주기)은 **별도 프로젝트**다. 이 설계에 포함하지 않는다.

## 1. 프롬프트 분리

잠긴 세 절(`역할`·`절대 규칙`·`추천 유형`)은 `build_system_prompt` 안에 그대로 둔다.
열어 줄 다섯 절만 파일로 뺀다.

```
data/prompt/
  judgment_criteria.md   # 판단 기준
  buy_target.md          # 목표 매수가 작성 지침
  sell_target.md         # 목표 매도가 작성 지침
  outlook.md             # 오늘 전망 작성 지침
  reason.md              # 근거 작성 지침
  version                # "v12"
  history/
    v11/                 # 그 버전의 다섯 파일 사본 + why.md
```

절마다 파일 하나로 두는 이유: 에이전트가 한 절만 갈아끼우기 쉽고, 변경 diff가 그대로
읽히며, JSON 이스케이프 문제가 없다.

파일에는 `## 판단 기준 ...` 헤더 줄을 **포함해** 저장한다 — 조립할 때 헤더를 따로 붙이면
에이전트가 헤더를 바꾸고 싶어도 못 바꾸고, 코드가 헤더 문구를 알아야 한다.

**폴백**: 파일이 없거나 읽을 수 없거나 비어 있으면, 코드에 박힌 현재 문구를 쓴다.
파일이 깨져도 추천이 멈추지 않는다. `data/prompt/`가 아예 없는 첫 실행이 정상 상태다.

**반영 시점**: `build_system_prompt`가 호출될 때 파일을 읽으므로, 그날 저녁 수정이 다음 날
09:02 추천에 **엔진 재시작 없이** 반영된다. 엔진이 시작 시점 `Settings`를 들고 도는 기존
설정과 다른 동작이므로 문서에 명시한다.

## 2. 버전

`data/prompt/version` 파일이 실제 버전을 들고, 에이전트가 고칠 때마다 올린다 (`v11` → `v12`).
`recommendations.prompt_version`에 그 값이 저장되어 버전별 집계의 기준이 된다.

코드 상수 `PROMPT_TEMPLATE_VERSION`은 **폴백용 기본 버전**으로 남는다. `version` 파일이
없으면 그 값을 쓴다.

## 3. 실행 통로

`SCHEDULED_ACTIONS`에 단계를 더해 `ActionRunner`의 같은 큐를 탄다. `REPORT_TIME`(15:35)에
`review_recommendations` **다음**으로 등록한다 — 그날 검증이 끝나야 판단 재료가 완성된다.
`TimeScheduler.due_jobs`가 등록 순서대로 돌려주고 큐가 FIFO이므로 순서가 지켜진다.

`touches_orders=False`다 — LLM 호출과 파일 쓰기가 이벤트 루프를 막지 않게 별도 스레드에서
돈다. 기존 `_trading_days_only`로 감싸 거래일에만 돈다.

UI 즉시 실행 버튼은 더하지 않는다.

## 4. 에이전트가 받는 것

- **버전별 집계** (최근 10거래일) — `prompt_version`별 건수, 목표 매수가 도달률,
  목표 매도가 도달률, 평균 실제 등락률
- **개별 행** — 그 구간의 종목·`outlook`·`review`·실제 고/저/종·도달 여부
- **현재 다섯 절의 전문**
- **잠긴 세 절의 전문 (읽기용)** — 모순되는 지시를 쓰지 않게 하기 위함이며, 고칠 수 없다고
  명시한다
- **이전 변경 이력의 `why.md`** — 자기가 지난번에 왜 고쳤는지 알아야 왔다 갔다 하지 않는다

검증되지 않은 행(`actual_close IS NULL`)은 집계에서 뺀다 — 대조할 것이 없다.

## 5. 에이전트가 내는 것

구조화 출력(json_schema)으로 형식을 강제한다.

```json
{
  "change": true,
  "reason": "왜 고치는가 / 왜 고치지 않는가",
  "sections": {"outlook": "## 오늘 전망 작성 지침\n..."}
}
```

- `sections`의 키는 **파일 이름(확장자 제외)**이다: `judgment_criteria`, `buy_target`,
  `sell_target`, `outlook`, `reason`. 이 다섯 개가 전부이며, 스키마의 `enum`으로 강제한다.
  값은 헤더 줄을 포함한 그 절의 **전문**이다.
- `change: false`면 아무것도 하지 않는다. **표본이 얇거나 신호가 없으면 넘어가는 것이
  정상 동작이다** — 매일 도는 것과 매일 바뀌는 것은 다르다.
- `sections`에는 **고칠 절만** 담는다.
- 프롬프트에 명시한다: 근거로 삼은 수치를 `reason`에 인용할 것, 표본이 부족하면 고치지 말 것,
  잠긴 절은 고칠 수 없다는 것.

## 6. 안전장치

코드가 적용 전에 검사한다. 하나라도 걸리면 그 절을 버리거나(부분) 전체를 버린다.

검사 순서대로 적는다. 절 개수 검사가 **가장 먼저**이며, 걸러내기 전의 원본 개수를 센다 —
걸러낸 뒤 개수를 세면 에이전트가 잘못된 절을 섞어 보내는 것으로 제한을 우회할 수 있다.

| 순서 | 검사 | 걸리면 |
|---|---|---|
| 1 | `sections`의 항목이 2개를 넘는다 (걸러내기 전 원본 기준) | **전체를 버린다** — 무엇이 효과가 있었는지 분리할 수 없다 |
| 2 | 키가 허용된 다섯 이름이 아니다 | 그 항목만 무시하고 로그에 남긴다. 잠긴 절 이름(`역할`·`절대 규칙`·`추천 유형`)이면 그 사실을 함께 남긴다 |
| 3 | 값이 비었거나 50자 미만이다 | 그 항목만 무시한다 |
| — | LLM 호출이 실패했다 | 아무것도 하지 않는다 |
| — | 걸러내고 남은 항목이 없다 | `change: false`와 같이 취급한다 |

스키마의 `enum`이 이미 키를 다섯 개로 제한하지만, 검사 2를 코드에도 둔다 — 스키마는
모델이 지키는 소프트 제약이고, 잠긴 절이 실제로 반영되는 것은 고장이기 때문이다
(`drop_other_setups`가 프롬프트의 유형 제한을 코드로 한 번 더 자르는 것과 같은 이유다).

파일 쓰기가 실패하면 경고 로그만 남기고 넘어간다 — 다음 날 추천은 이전 프롬프트로 정상
동작한다.

## 7. 이력과 되돌리기

프롬프트를 고치기 **전에** 현재 다섯 파일을 `data/prompt/history/<현재 버전>/`으로 복사하고,
같은 폴더에 `why.md`(에이전트의 `reason`)를 쓴다. 그 뒤 새 내용을 쓰고 `version`을 올린다.

되돌리려면 그 폴더의 파일들을 `data/prompt/`로 되돌려 놓으면 된다. 자동 되돌리기는 만들지
않는다.

## 8. 메일

**실제로 고친 날만** 한 통 나간다. `change: false`인 날은 보내지 않는다.

- 제목: `[AutoTrade] 2026-09-08 추천 프롬프트 수정 (v11 → v12)`
- 본문(평문): 에이전트의 `reason`, 근거가 된 버전별 집계 표, 고친 절의 before/after 전문,
  그리고 되돌리는 방법 한 줄(`data/prompt/history/v11/`의 파일을 `data/prompt/`로 복사)

## 9. 문서

`주식자동매매_PRD.md`에 절을 더한다.

- 프롬프트 다섯 절이 파일로 분리되어 **엔진 재시작 없이** 다음 추천에 반영된다는 것
- 잠긴 세 절과 그 이유(코드와의 계약)
- 에이전트의 실행 시각·판단 근거·안전장치·이력·되돌리는 방법
- `prompt_version`이 이제 코드 상수가 아니라 파일 값이라는 것

`CLAUDE.md`의 스케줄 나열과 "설정은 `.env` 하나로 통일" 서술도 함께 확인한다 — 프롬프트가
`.env` 밖의 새 상태 저장소가 되므로 그 문장이 어긋난다.

## 10. 테스트

| 대상 | 내용 |
|---|---|
| 프롬프트 조립 | 파일이 없으면 코드 기본값으로 폴백, 파일이 있으면 그 내용이 들어감, 파일이 비면 폴백 |
| 버전 | `version` 파일이 없으면 `PROMPT_TEMPLATE_VERSION`, 있으면 파일 값 |
| 집계 | 검증된 행만, `prompt_version`별로 묶임 |
| 안전장치 | 잠긴 절 무시, 알 수 없는 절 무시, 짧은 본문 무시, 3절 이상이면 전체 폐기, 남은 절이 없으면 무변경 |
| 적용 | 이력 폴더에 이전 버전과 `why.md`가 남고, 새 내용이 쓰이고, 버전이 오름 |
| `change:false` | 파일도 버전도 바뀌지 않고 메일도 안 나감 |
| 실패 | LLM 실패 시 무변경, 파일 쓰기 실패 시 흐름 유지 |
| 메일 | before/after와 집계 표가 실림 |

## 받아들인 위험

사용자가 알고 택한 것들이다. 나중에 이 문서를 읽을 때 "왜 이렇게 했나"를 되짚기 위해 남긴다.

**표본이 얇다.** 하루 추천이 2~3종목이라 10거래일이어도 20~30건이다. PRD 10절의 익절 분석은
27건/12거래일을 놓고도 "표본이 작다"는 전제 위의 재판단이라고 적고 있다. 완화책은 두 가지다 —
버전별로 나눠 보여주어 표본이 얇다는 사실이 에이전트에게 숫자로 드러나게 한 것, 그리고
`change: false`를 정상 선택지로 둔 것.

**표류 위험.** LLM이 얇은 표본으로 자기 지시문을 매일 고치면, 개선이 아니라 무작위 보행이 될
수 있다. 실제 사례가 있다 — 2026-09-04에 관찰된 "당일 거래량을 근거로 인용하는" 문제는 아무도
고치지 않았는데 나흘 뒤 스스로 사라졌다. 에이전트가 그때 개입했다면 그 개선을 자기 수정의
공으로 착각했을 것이다. 완화책은 한 번에 2절 제한과 이력의 `why.md`를 다시 입력으로 주는 것뿐이며,
근본적으로는 **사람이 변경 메일을 읽고 판단하는 것**에 기댄다.

**실전 계좌에 직접 영향이 간다.** 이 프롬프트가 어떤 종목을 살지 정한다. 승인 절차가 없으므로,
나쁜 수정은 사람이 메일을 읽고 되돌릴 때까지 유효하다.
