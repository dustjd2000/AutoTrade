# 추세 필터와 뉴스 검증 (2026-10-01)

**문제**: 1호 전략이 하락 추세 종목을 반복해서 산다. 크래프톤을 9/29에 사서 잃고, 10/01에
**더 떨어졌다는 이유로 더 높은 점수를 줘서** 다시 샀다. 그리고 "회사가 구조적으로 나쁘다"를
시스템이 볼 방법이 아예 없다.

**해결**: ① 이평 추세를 계산해 프롬프트에 싣는다(추가 호출 0). ② 추천된 종목만 웹검색으로
악재를 확인하고, 걸리면 그 종목을 빼고 1회 재추천한다.

---

## 1. 배경 — 무엇이 관측됐나

### 1.1 추천 자체는 "떨어진 종목"을 사도록 설계돼 있다

2026-08-20에 추천 유형을 낙폭 되돌림(`rebound`)만으로 제한했다(PRD 5.5-B). DB의 추천 35건이
전부 `setup=rebound`다. `judgment_criteria`의 1순위가 이렇게 적혀 있다:

> **최근 가격대에서의 위치 — 낙폭이 얼마나 큰 상태인지**가 이번 선별의 전제입니다. (…)
> 이동평균 아래로 내려와 있거나 최근 저가에 가까울수록 낙폭이 큰 상태이며 (…)

즉 "안 좋아서 떨어진 종목"을 고르는 것이 의도다. 문제는 그 지시에 **일시적 눌림과 추세 하락을
가르는 기준이 없다**는 것이다.

### 1.2 크래프톤 2건이 그 약점의 전형이다

| | 9/29 | 10/01 |
|---|---|---|
| 추천가 | 202,000 | 197,400 |
| 이동평균 | 211,105 | **207,726** |
| 이평 대비 | -4.3% | **-5.9%** |
| 전일 거래량 배수 | **0.93배** | 1.64배 |
| 결과 | -0.90% 마감 | -15,632원 |

떨어질수록 이평 괴리가 커지고, 괴리가 커질수록 점수가 올라간다. 이평 자체가
211,105 → 207,726으로 내려갔지만 **프롬프트는 그날의 이평 값만 받고 방향은 받지 않는다.**

9/29 건은 전일 거래량이 평균의 0.93배였다 — 프롬프트 스스로 "2배 이상이면 재료가 발생한
것이니 무겁게 보라"고 하는데, **재료 없이 그냥 흘러내린 것**이 쇼트리스트에 들었다.

### 1.3 시스템은 "회사가 안 좋다"를 볼 수 없다

LLM에 넘기는 입력은 전일 OHLCV·거래량 급증 배수·최근 20일 고가/저가/이동평균·전일 변동폭·
당일 현재가/등락률·DART 공시 **제목**이 전부다. 실적도 뉴스 본문도 업황도 없다. 악재는 DART
공시 제목이 `BLOCKING_KEYWORDS`에 걸릴 때만 걸러진다.

웹검색으로 같은 종목을 물었더니 이렇게 답했다:

> 역대급 실적에도 불구하고 주가가 계단식 하락 중. 주력 IP 배틀그라운드의 트래픽 감소,
> 신작 모멘텀 부재, 무배당 기조에 대한 투자자 불만이 지속 보도.

이 정보는 현재 입력 어디에도 없다.

## 2. 실측 — 설계를 결정한 숫자

`claude-sonnet-5`, 종목 2개 기준(스크래치패드 프로브).

| 구성 | 소요 | 입력 토큰 | 검색 | JSON |
|---|---|---|---|---|
| 스키마만 (현행 추천) | 6.7초 | 381 | – | OK |
| 웹검색만 | 84.5초 | 72,888 | 13 | 실패(산문) |
| 웹검색 + 스키마, 2종목 한 번에 | **238.0초** | 189,232 | 6 | OK |
| **종목별 병렬, `max_uses=3`, `effort=low`** | **29.9초** | 132,969 | 3+3 | OK |
| 종목별 병렬, `max_uses=5`, `effort=medium` | 116.8초 | 63,315 | 5+3 | OK |

**확정된 사실:**

- 웹검색과 `output_config.format`(json_schema)은 **함께 쓸 수 있다.** 문서가 명시하지
  않아(Citations는 400) 실제로 호출해 확인했다.
- 종목별로 쪼개 병렬 호출하고 `max_uses`를 걸면 238초 → 30초로 떨어진다.
- **편차가 크다.** 같은 모양에서 28초와 117초가 나왔다. 꼬리를 기준으로 설계한다.
- `web_search_20260209`는 `claude-sonnet-5`에서 동작한다.

**발견된 실패 모드**: `max_uses`에 걸려 확인을 못 했는데 모델이 `blocking: false`
("특이사항 없음")로 답했다. 실제 응답:

> "웹 검색 도구 사용 제한으로 추가 조회가 불가능하여 (…) 확인하지 못했으며, 확인된 특이사항은 없음"

**"확인 못 함"과 "악재 없음"을 스키마에서 갈라야 한다.**

## 3. 설계 A — 추세 필터

### 3.1 무엇을 계산하나

[`market_data.py`](../../../src/api/market_data.py)의 `get_previous_day_metrics`는 이미 최근
20거래일 종가 전체(`closes`)를 들고 있으면서 평균만 쓰고 버린다. 거기서 단기 이평을 함께
낸다. **추가 API 호출이 없다.**

- `short_moving_average` — 최근 5거래일 종가 평균 (당일 제외)
- 기존 `moving_average`(20일)와의 비율이 추세다

`PreviousDayMetrics`와 `DailyStockData`에 필드를 하나씩 더하고, 봉이 5개 미만이면 `0.0`
(= 산출 안 됨, 거래량 급증 배수와 같은 규약).

### 3.2 프롬프트에 어떻게 싣나

후보 줄에 한 토막을 더한다:

```
... / 이동평균 207,726 / 5일 이평 198,420 (20일 대비 -4.5%) / ...
```

해석은 코드가 하지 않고 비율만 준다 — "하락 추세"라는 말을 코드가 붙이면 그 라벨이 근거로
쓰이고, 경계값 하나가 판정을 가른다.

### 3.3 어느 절에 지시를 넣나 — 잠긴 절이다

`judgment_criteria`는 **15:35 튜너가 고칠 수 있는 절**이라, 거기 넣으면 자동 수정이 지울 수
있다. 추세 요건은 사람이 정한 규칙이므로 **잠긴 절(`절대 규칙`)에 넣는다** — 추천 유형 제한을
잠근 것과 같은 이유다(PRD 5.13 "왜 세 절은 잠갔나").

### 3.4 코드로 거르지 않는다

사용자 결정(2026-10-01): 추세도 뉴스도 **프롬프트 재료로만** 주고 코드는 후보에서 빼지 않는다.

**받아들인 위험**: 2026-09-18(손절선)과 2026-10-01(노이즈 고점)에 두 번 확인된 패턴 —
"지시보다 데이터가 세다" — 에 따르면 LLM이 추세 지시를 무시할 수 있다. 다만 여기서는 금지
문장이 아니라 **새 데이터를 주는 것**이고, 거르는 쪽이 아니라 재료를 늘리는 쪽이라 실패해도
현행과 같아진다. 효과는 추천 검증(PRD 5.12)에 쌓이는 표본으로 확인한다.

## 4. 설계 B — 뉴스 검증

### 4.1 흐름

```
09:02 추천 (현행)
   ↓ 추천된 N종목
      검증 (종목별 1회, 병렬)
   ↓ blocking 종목 있음?
      ├ 없음 → 그대로 매수 대상
      └ 있음 → 탈락 종목 제외하고 재추천 1회 → 새 종목만 재검증
   ↓
09:10 매수 (09:05에서 이동)
```

**재추천은 1회로 제한한다.** 2회부터 꼬리 시간이 폭발하고, 세 번째 추천은 이미 두 번 걸러낸
뒤라 후보 질도 떨어진다.

### 4.2 새 모듈 `src/llm/news_verifier.py`

기존 `recommender.py`/`exit_advisor.py`와 같은 꼴을 따른다 — 스트리밍, `max_retries=0`,
`deadline`으로 예산 직접 관리, 실패 시 `None`.

```python
@dataclass
class NewsVerdict:
    ticker: str
    checked: bool    # 웹검색이 실제로 확인했는가
    blocking: bool   # 오늘 매수를 피할 만한 구체적 악재가 있는가
    reason: str
```

- 툴: `[{"type": "web_search_20260209", "name": "web_search", "max_uses": 3}]`
- `output_config`: `{"format": {"type": "json_schema", ...}, "effort": "low"}`
- 종목별 1회 호출, `ThreadPoolExecutor`로 병렬
- 스키마에 `checked`를 **반드시** 둔다 (2절 실패 모드)

### 4.3 `blocking`의 정의

프롬프트가 못 박는다: **최근 2주 내, 주가에 불리한 구체적 사건.** 실적 하향, 신작·수주 부진,
지분 희석, 규제·소송, 애널리스트 목표가 하향.

"주가가 떨어지고 있다"는 **악재가 아니다** — 그건 이 전략이 노리는 조건 자체다. 프롬프트에
명시하지 않으면 모든 추천 종목이 탈락한다(전부 낙폭 종목이므로).

### 4.3-1 '절대 규칙 2'와 어긋나지 않는다

추천 프롬프트의 잠긴 절에는 이런 금지가 있다([`recommender.py:193`](../../../src/llm/recommender.py#L193)):

> 학습 데이터의 기억(종목 평판, 과거 주가)에 의존하지 마십시오 — 절대 규칙 2와 같습니다.

검증은 이 규칙을 **어기지 않고 오히려 지킨다.** 금지된 것은 *모델의 기억*이고, 검증이 쓰는
것은 *그 자리에서 검색한 현재 기사*다. 실제로 프로브에서 웹검색 없이 물었을 때
(측정 A) 모델은 기억만으로 "중국 판호 불확실성" 같은 **오래되고 검증되지 않은 내용**을
사실처럼 답했다. 검증 프롬프트는 "검색 결과에 근거하지 않은 내용을 쓰지 말 것"과
"근거 기사가 없으면 `checked=false`"를 못 박아 같은 함정을 막는다.

### 4.4 실패는 전부 "종전대로 매수"

| 상황 | 동작 |
|---|---|
| LLM 호출 실패·타임아웃 | 통과 |
| 형식 오류·파싱 실패 | 통과 |
| `checked=false` (확인 못 함) | 통과, 단 로그·메일에 구분해 남김 |
| 예산 부족으로 검증 생략 | 통과 |
| 예산 부족으로 재추천 생략 | 1차 통과분만 매수 |

검증은 **추가 안전장치지 관문이 아니다.** 막으면 그날 매매가 통째로 빠지고, 통과시키면
지금까지 해온 것과 같은 상태일 뿐이다. 이것은 AI 매도 판단이 "실패 = 팔지 않음"으로 떨어지는
것과 같은 원칙이다 — **실패가 현상 유지로 떨어진다.**

### 4.5 시간 예산

| 단계 | 중앙값 | 꼬리 |
|---|---|---|
| 추천 | 7초 | 340초 (2026-09-15·16 실측) |
| 검증 | 30초 | 120초 |
| 재추천 + 재검증 | 0 | 460초 |
| **합** | **37초** | **920초** |

`BUY_TIME` 09:05 → **09:10** (사용자 결정). 추천 +8분이다. 중앙값이면 09:03에 끝나고,
꼬리에서는 재추천을 버리고 1차 통과분만 산다.

예산 배분은 기존 `budget_seconds(buy_time, now)`를 그대로 쓰되 단계마다 남은 시간을 다시 재서
넘긴다. **남은 시간이 검증 최소치(60초) 미만이면 검증을 건너뛴다** — 반쯤 하다 마는 것보다
안 하는 것이 낫다.

### 4.6 09:10으로 미루는 대가

- 진입이 5분 늦어 되돌림 구간을 놓칠 수 있다. 2026-08-20에 09:10 → 09:08, 08-21에 09:05로
  **당겨온 것을 되돌리는 셈**이다 (PRD 10절).
- 10:10 미체결 취소까지의 시간이 5분 줄어 지정가 체결 기회가 그만큼 준다.
- `Settings.validate()`의 "매수는 추천 +3분 이상" 요건은 그대로 만족한다.

## 5. 기록과 알림

`recommendations` 테이블에 3열을 더한다:

| 열 | 뜻 |
|---|---|
| `news_checked` | 웹검색이 실제로 확인했는가 (0/1) |
| `news_blocking` | 악재로 판정됐는가 (0/1) |
| `news_reason` | 판정 근거 한 문장 |

탈락해서 매수하지 않은 종목도 **행을 남긴다** — 탈락 판정이 옳았는지 되짚으려면 그 종목의
그날 실제 움직임이 필요하고, 그건 15:35 추천 검증(PRD 5.12)이 이미 채워 준다.

추천 결과 메일에 검증 결과와 탈락·대체 내역을 싣는다.

## 6. 테스트

- `news_verifier`: 스키마 파싱, `checked=false` 분리, 호출 실패 시 `None`, 타임아웃,
  병렬 호출이 종목 수만큼 나가는지 — LLM은 가짜 클라이언트로 대체(기존 테스트와 같은 방식)
- 워크플로: 탈락 0건이면 재추천 안 함 / 탈락 1건이면 재추천 1회 / 재추천 결과도 탈락이면
  더 돌지 않음 / 예산 부족 시 검증·재추천 생략 / 검증 실패 시 전원 통과
- 추세: 5일 이평 산출, 봉 5개 미만이면 0.0, 후보 줄에 실리는지
- 프롬프트: 추세 지시가 **잠긴 절**에 있어 `sanitize_sections`가 건드릴 수 없는지

실제 웹검색을 때리는 테스트는 두지 않는다 — 네트워크·비용·비결정성이 전부 들어온다.
